# State Machines

## Order Status (`order_status`)

```
                    ┌─────────┐
                    │   NEW   │ ◄── створення замовлення
                    └────┬────┘
                         │
                    ┌────▼──────┐
               ┌────│ CONFIRMED │
               │    └────┬──────┘
               │         │
               │    ┌────▼───────┐
               │    │ PROCESSING │
               │    └────┬───────┘
               │         │
               │    ┌────▼────┐
               ├────│ SHIPPED │──────────┐
               │    └────┬────┘          │
               │         │              │
               │    ┌────▼──────┐  ┌────▼─────┐
               │    │ DELIVERED │  │ RETURNED  │
               │    └────┬──────┘  └──────────┘
               │         │
               │    ┌────▼──────┐
               │    │ COMPLETED │
               │    └───────────┘
               │
          ┌────▼──────┐
          │ CANCELLED │
          └───────────┘
```

### Дозволені переходи

| З | В | Коментар |
|---|---|----------|
| `NEW` | `CONFIRMED` | Адмін підтвердив замовлення |
| `NEW` | `CANCELLED` | Адмін скасував (немає товару, помилка, тощо) |
| `CONFIRMED` | `PROCESSING` | Замовлення в обробці (збірка) |
| `CONFIRMED` | `CANCELLED` | Скасування до відправки |
| `PROCESSING` | `SHIPPED` | Передано перевізнику (ТТН виписана) |
| `PROCESSING` | `CANCELLED` | Скасування до відправки |
| `SHIPPED` | `DELIVERED` | Клієнт отримав |
| `SHIPPED` | `RETURNED` | Повернення після відправки |
| `DELIVERED` | `COMPLETED` | Замовлення закрите (фінальний статус) |

**Побічний ефект:** будь-який перехід у `CANCELLED` (і назад із нього) автоматично змінює `payment_status` — див. [Крос-машинне правило: скасування замовлення](#крос-машинне-правило-скасування-замовлення).

**Note:** Поточна реалізація не валідує переходи — адмін може встановити будь-який статус через `PATCH /orders/:id/status`. Валідація переходів — кандидат на майбутню реалізацію. Побічний ефект на `payment_status` при скасуванні, натомість, реалізований.

## Payment Status (`payment_status`)

```
                    ┌─────────┐
                    │ PENDING │ ◄── створення замовлення (завжди)
                    └────┬────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
     ┌────▼──┐      ┌────▼───┐     ┌────▼───┐
     │ PAID  │      │ FAILED │────►│ VOIDED │ ◄── order_status → CANCELLED
     └───┬───┘      └────────┘     └────────┘
         │
    ┌────▼─────┐
    │ REFUNDED │
    └──────────┘
```

### Дозволені переходи

| З | В | Коментар |
|---|---|----------|
| `PENDING` | `PAID` | Оплата підтверджена (LiqPay callback автоматично, або адмін вручну для IBAN/CASH/COD) |
| `PENDING` | `FAILED` | Оплата не пройшла (LiqPay callback зі статусом failure/error) |
| `PENDING` | `VOIDED` | Замовлення скасоване, кошти не надходили — виставляється **автоматично** |
| `FAILED` | `VOIDED` | Те саме: скасування замовлення після невдалої оплати — **автоматично** |
| `PAID` | `REFUNDED` | Повернення коштів (вручну, після реального рефанду) |
| `VOIDED` | `PENDING` | Розскасування замовлення (`CANCELLED` → активний статус) — **автоматично** |
| `FAILED` | `PENDING` | Два джерела, обидва **автоматичні**. (1) Клієнт змінив спосіб оплати з LiqPay на офлайн (`PATCH /orders/lookup/:n/payment-method`, `PATCH /orders/me/:id/payment-method`): відхилена спроба карткою не є фактом про IBAN/COD/CASH-замовлення. (2) Клієнт відкрив повтор оплати карткою і клейм видано (`POST /liqpay/checkout`, з 2026-09-08): сесія знову жива, тож і статус знову `PENDING` — це те, що не дає другій вкладці відкрити другу сесію. Див. [TD-0009](../designs/TD-0009-customer-payment-method-change.md) і абзац про одну живу сесію нижче |

**Note:** Для IBAN/CASH/COD оплата підтверджується адміном вручну (`PATCH /orders/:id/payment-status`). Для **накладного платежу** (`COD`) гроші приходять уже після вручення: замовлення лишається `PENDING` увесь час доставки, і адмін ставить `PAID` після перерахунку від Нової Пошти. Автоматичного зв'язку з `DELIVERED` або з встановленням ТТН немає. Для **LiqPay** підтвердження автоматичне: server-to-server callback `POST /liqpay/callback` переводить `PENDING → PAID` (ідемпотентно, з перевіркою підпису та суми) і надсилає лист. Див. [ADR-0009](../adr/0009-online-payment-liqpay.md).

**Note:** `VOIDED` («Скасовано») означає, що оплата вже не очікується, бо замовлення скасоване і кошти не надходили. Це не те саме, що `REFUNDED` — той описує реальне повернення вже отриманих коштів. Див. [TD-0003](../designs/TD-0003-order-cancellation-payment-status.md).

## Крос-машинне правило: скасування замовлення

`order_status` і `payment_status` — незалежні машини станів з одним винятком: скасування замовлення. `PATCH /orders/:id/status` разом зі зміною `order_status` перераховує `payment_status` за таблицею нижче.

| `order_status` | Поточний `payment_status` | Новий `payment_status` | Чому |
|----------------|---------------------------|------------------------|------|
| → `CANCELLED` | `PENDING` | `VOIDED` | Кошти не надходили — оплата вже не очікується |
| → `CANCELLED` | `FAILED` | `VOIDED` | Те саме; `FAILED` перестає бути актуальним |
| → `CANCELLED` | `PAID` | **не змінюється** | Гроші реально отримані. Адмін виконує повернення і вручну ставить `REFUNDED` |
| → `CANCELLED` | `REFUNDED` | **не змінюється** | Уже термінальний |
| `CANCELLED` → активний | `VOIDED` | `PENDING` | Розскасування: оплата знову очікується |

**Пізній callback платіжного шлюзу.** Якщо LiqPay підтверджує оплату вже після скасування замовлення (`POST /liqpay/callback` → `applyGatewayPaymentResult`):

- `success`/`sandbox` → `payment_status` стає `PAID` і зберігається `payment_transaction_id` (кошти реально надійшли, приховувати їх не можна), але **клієнтський лист «оплату отримано» не надсилається** — замість нього йде service-лист адміну про потребу повернення. `order_status` лишається `CANCELLED`.
- `failure`/`error` → нічого не змінюється, `VOIDED` зберігається.

## Крос-машинне правило: зміна способу оплати клієнтом

Покупець може перевести **неоплачене** замовлення (`payment_status ∈ {PENDING, FAILED}`,
`order_status ∈ {NEW, CONFIRMED}`) з LiqPay на `COD` / `IBAN` / `CASH` (з тим самим правилом
сумісності з доставкою, що й на чекауті — тепер серверним: `CASH` лише `PICKUP`, `COD` лише
`NOVA_POST`/`COURIER`). Від `PROCESSING` посилка може вже нести накладну накладного платежу, тож
далі спосіб міняє лише адмін. Запис умовний і пінить прочитаний стан разом із поточним методом:
callback або друга вкладка, що встигли між читанням і записом, роблять його промахом (перечит →
або той самий метод уже стоїть = no-op, або `409 PAYMENT_METHOD_LOCKED`). Див.
[TD-0009 §5.4.1](../designs/TD-0009-customer-payment-method-change.md).

**Пізній callback LiqPay після зміни способу оплати.** LiqPay знає лише номери, які ми віддали йому,
коли замовлення було LiqPay-замовленням, тож callback для іншого методу означає, що покупець змінив
метод під час живої сесії. Кожен запис callback-у пінить метод:

| Callback | `payment_method` зараз | Результат |
|---|---|---|
| `failure`/`error` | `≠ LIQPAY` | нічого не змінюється — мертва карткова сесія не має зробити COD-замовлення `FAILED` |
| `success`/`sandbox` | `≠ LIQPAY` | `payment_status = PAID`, **`payment_method` повертається на `LIQPAY`** (гроші реально прийшли карткою), `payment_transaction_id` зберігається; клієнту — лист «оплачено», сервісу — лист «не збирати накладний платіж/IBAN». Якщо `order_status` уже поза `NEW`/`CONFIRMED`, сервісний лист має тему «ТЕРМІНОВО … зняти … на ТТН №…» — єдиний запобіжник від повторної оплати на пошті — людина |

**Одна жива сесія LiqPay на замовлення.** `POST /liqpay/checkout` клеймить сесію умовним записом
`liqpay_checkout_started_at`: доки платіж `PENDING`, друга сесія в межах 15 хв відхиляється
(`409 LIQPAY_SESSION_ACTIVE` з `retry_after_seconds`); `FAILED` — сесія, яку LiqPay сам закрив,
повтор дозволений одразу. Той самий залишок часу lookup віддає як `liqpay_retry_after_seconds`.
Адмінська зміна `payment_method` скидає штамп.

**Доповнення 2026-09-08 (аудит блоку I, рядки I-e, I-18).** Виданий клейм повтору сам переводить
`FAILED → PENDING` тим самим умовним записом (джерело переходу — `POST /liqpay/checkout`, не
адмінка й не callback). Перший повтор після невдачі лишається доступним **одразу**, як вирішено в
TD-0009 §5.4.3, але щойно payload виданий, замовлення читається як `PENDING` зі свіжим штампом —
тож друга вкладка вже не відкриє другу живу сесію для того самого повтору. Ціна цього видима:
покупець, який відкрив повтор і покинув його, чекає ті самі 15 хв (або міняє спосіб оплати) — та
сама прийнята ціна, що вже діяла для першої спроби. Реквізити провайдера читаються **до** клейму,
тож недоступний шлюз відповідає `503 LIQPAY_UNAVAILABLE` і не лишає покупцю годинника за сесію,
якої не було.

## Product Variant Status (`status`)

```
  ┌───────┐
  │ DRAFT │ ◄── створення (якщо вказано)
  └───┬───┘
      │
  ┌───▼────┐
  │ ACTIVE │ ◄── за замовчуванням при створенні
  └───┬────┘
      │
  ┌───▼──────┐
  │ ARCHIVED │
  └──────────┘
```

| Статус | В каталозі | В замовленні |
|--------|-----------|-------------|
| `draft` | Не показується | Не можна додати |
| `active` | Показується | Можна додати |
| `archived` | Не показується | Існуючі замовлення зберігаються |

Фільтр каталогу: `status = "active"` (hardcoded в агрегації).

## Discount Coupon Lifecycle

```
  Створення (адмін)
       │
       ▼
  ┌──────────────┐
  │  is_active   │ ◄── true за замовчуванням
  │  valid_until │ ◄── дата закінчення
  └──────┬───────┘
         │
    Валідація при checkout:
         │
         ├── code не знайдено      → { valid: false, reason: "NOT_FOUND" }
         ├── is_active = false     → { valid: false, reason: "INACTIVE" }
         ├── valid_until < now     → { valid: false, reason: "EXPIRED" }
         └── все ок                → { valid: true, coupon: {...} }

    При створенні замовлення:
         │
         └── Snapshot в order.applied_discount:
             { coupon_id, code, discount_percent, discount_amount }
```

**Note:** Купон не має лічильника використань — один код можна використати необмежену кількість разів до закінчення терміну дії або деактивації адміном.
