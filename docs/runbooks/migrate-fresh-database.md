# Нова база з дампа: міграція каталогу

Перевірено 2026-09-10 на `~/Desktop/db_backup_for_test`: відновлення каталогу в новому
MongoDB 7, повний ланцюг 12 кроків у два проходи, третій apply без змін документів.
Результат: 44 товари, 301 варіант, 293/293 кольорові варіанти зі словником із 122 кольорів,
14 лендінгів із текстами та FAQ. Публікація лендінгів лишається ручною.

## Перед запуском

1. Відновити свіжий повний BSON-дамп у **нову** базу зі збереженням ObjectId та індексів.
2. Запускати міграції локально з checkout backend із виправленнями аудиту від 2026-09-10
   та встановленими залежностями. DATABASE_URL має вести на нову відновлену базу.
3. У середовищі запуску явно задати `DATABASE_URL` із назвою нової бази та
   `MIGRATION_REPORT_DIR` — окрему постійну теку для її звітів. Не використовувати звіти
   dev-бази. Runner показує host і назву бази без пароля та перевіряє наявність каталогу.
4. До завершення не підключати до нової бази покупців, адмінські записи чи синхронізацію
   залишків. Старий сайт може продовжувати працювати зі старою базою; перенесення замовлень,
   які надійшли після дампа, треба врахувати окремо під час перемикання.

## Команди локально з кореня backend

```bash
# Спершу репетиція на тому самому свіжому дампі (потрібні Docker і mongorestore):
yarn migrate:rehearse /path/to/dump

# Потім на новій базі, після явного встановлення DATABASE_URL і MIGRATION_REPORT_DIR:
yarn migrate --dry-run --include-colors
yarn migrate --include-colors --yes
yarn migrate:verify
```

`--include-colors` потрібний для всіх 12 кроків, включно з кольорами та короткими назвами.
Звичайний `yarn migrate` утримує два останні кроки для старого сценарію деплою на чинний сайт.
Для нової ще не підключеної бази можна виконати повний ланцюг одразу.

Перший dry-run не застосовує попередні кроки, тому може зупинитися на порожньому словнику
кольорів: seed був лише змодельований. Це не заміна репетиції на дампі. Після повного apply
фінальна перевірка запускається автоматично; `yarn migrate:verify` повторює її окремо.
Успіх вимагає exit 0, а не лише напису «Chain complete» в середині журналу.

## Що перевірено та виправлено

- Помилка mongorestore тепер зупиняє репетицію; неоднозначний чи неповний дамп відхиляється.
- Кожна репетиція має новий контейнер і випадковий локальний порт; не чіпає спільну тестову базу.
- BSON-знімки доводять, що dry-run не змінює документи, а третій apply не має змін.
- Runner відхиляє невідомі прапорці, суперечливі режими та порожню/не ту базу.
- Повна перевірка знаходить незавершені фільтри, кольори, ваги, назви, лендінги та пошкоджені зв'язки.
- Перейменування відновлюється після обриву між записом товару й варіантів; початкові URL
  зберігаються до першого запису в `rename-journal.json`. Повторний apply/dry-run їх не стирає.
- Dry-run ізольований від робочих звітів; звіти apply архівуються по проходах у `history/`.
- Колірна міграція відхиляє зайнятий стороннім варіантом URL до записів, перевіряє прочитані
  поля перед оновленням і не замінює пошкоджений slug-map новим порожнім файлом.

Перевірки: 493 наявні Jest-тести міграцій/словника та 8 регресійних тестів запуску, відновлення,
відкату, колізій і повноти каталогу (включно з реальним MongoDB). Нові регресії: `yarn migrate:test`;
Mongo-сценарій вмикається через `TEST_MIGRATION_URI` із локальної репетиції.

## Після міграції

Переглянути та опублікувати лендінги, переписати опис рефілу, звірити розрахункові ваги,
встановити Google-категорію `499682`, оновити кеші нового фронтенду та sitemap. Публікація,
Google-кабінети, тарифи доставки та історичні міграції замовлень не входять до цього ланцюга
каталогу. Для відкату всього перенесення зберігати вихідний дамп і звіти на постійному сховищі.

Деталі прапорців і відкату: [README міграцій](../../repos/fillando-be/scripts/fillando_v_2/README.md).
Репетиція доводить роботу на перевіреному дампі; якщо дамп оновиться, повторити репетицію саме з ним.
